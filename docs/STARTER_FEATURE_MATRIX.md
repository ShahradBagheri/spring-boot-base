# Standalone consumption audit

Baseline: Spring Boot 4.1.2, Java 25. The current Maven coordinates are `io.github.shahradbagheri:<artifact>:0.1.0-M1`. The root `spring-boot-base` POM inherits Boot's starter parent and manages shared versions across the reactor. Only `base-mcp-server` imports the Spring AI 2.0.3 BOM. An external Maven build needs this parent POM available for library dependency resolution today. The consumer can use its own parent.

The matrices cover production POM dependencies and source-level wiring. Test dependencies stay scoped to the reactor. See [the module guide](MODULES.md) for the existing build and extension workflow.

## Activation and proposed starter boundaries

The current demo starts at `com.notshahrad.spring_boot_base`. Its Boot component, entity, and repository discovery cover the corresponding legacy packages in dependency JARs. An external app with its own root package needs targeted registration for those libraries. Today Boot discovers three base configurations independently of that package layout through `AutoConfiguration.imports`: WebSocket, SMTP, and MCP.

| Implementation | Current activation and runtime requirements | Demo integration and proposed boundary |
| --- | --- | --- |
| `base-core` | Plain Java types with no registration, flag, or external service. | Keep as a plain JAR, included where contracts are used, such as by `base-web-starter`. |
| `base-data-jpa` | Import `JpaAuditingConfiguration` and supply an `AuditorAware<String>` bean named `auditorAware`. Register consumer entities and repositories and configure a datasource, compatible driver, and schema when using JPA. | The demo's `JpaConfig` attributes writes through its security context, and its settings entity demonstrates `BaseEntity`. `base-data-jpa-starter` should make auditing and entity discovery explicit while leaving actor identity and application schema to the consumer. |
| `base-web` | Register `GlobalExceptionHandler` by component scan or explicit import in a Spring MVC app. The response types are plain Java contracts. | The demo discovers the advice through its root scan. `base-web-starter` should register the advice conditionally and let applications override it. |
| `base-websocket` | Servlet auto-configuration with `base.websocket.enabled=true`. Registers `/ws` and a single-instance STOMP broker with `/app` and `/topic` prefixes. `base.websocket.allowed-origins` defaults to same-origin access. | The demo owns broadcast handlers, handshake authentication, optional bearer support, and STOMP message policy. `base-websocket-starter` should expose the transport independently. Issue [#152](https://github.com/ShahradBagheri/spring-boot-base/issues/152) and merged [PR #153](https://github.com/ShahradBagheri/spring-boot-base/pull/153) already delivered the transport. |
| `base-security` | Import `SecurityConfig` or discover it by scanning. It imports the security exception advice, enables method security, and uses servlet security and a Jackson `JsonMapper`. Its default chain backs off by the bean name `securityFilterChain`. | The demo's root scan finds this baseline alongside feature-specific chains. `base-security-starter` needs an application-override contract that preserves a fallback for routes outside a feature's chain. |
| `base-auth` | Register auth JPA entities and repositories, JPA auditing, and `OidcIdentityService` when using local provisioning. Requires the local-user and external-identity schema (V2) and a datasource. No library flag. | The demo finds these types by scanning and applies V2. `base-auth-starter` should wire local identities and leave login methods and migrations application-owned. |
| `base-auth-oauth2` | Register `OidcLoginConfiguration` and set `base.auth.oauth2.enabled=true`. Needs the local identities setup, a servlet app with a `JsonMapper`, at least one client registration under `spring.security.oauth2.client`, and provider credentials and callbacks for Google or Apple. Supplies an OAuth2 route chain. | The demo provides example provider profiles and protected fallback routes. `base-auth-oauth2-starter` should activate only with explicit configuration, preserving the application's route policy. |
| `base-auth-token` | Register `AccessTokenConfiguration` and set `base.auth.token.enabled=true`. Needs issuer, audience, signing key ID and RSA key files, `JdbcTemplate`, a transaction manager, `JsonMapper`, and the V2–V4 schema. The library provides token issuing, verification and refresh services. | The demo selects bearer routes and wires token endpoints and optional WebSocket bearer authentication. `base-auth-token-starter` should supply reusable services while the app chooses routes and issuance policy. |
| `base-auth-email` | Register `EmailIdentityRepository` for `base.auth.email.enabled=true` (V2, V5). Add `EmailPasswordService` and `base.auth.email.password-enabled=true` for password and challenge flows (also V6). Uses the app's PostgreSQL datasource and JDBC transactions. | The demo owns signup/reset endpoints, session policy, client origin, and challenge delivery through `base-mail`. `base-auth-email-starter` should expose the identity and password services independently of the transport. |
| `base-mail` | Plain Java email sender, templates, and notification dispatch. Real delivery requires a supplied `EmailSender`. | The demo wires challenge templates and a sender. Keep the contract JAR independent so applications can supply another adapter. |
| `base-mail-smtp` | Boot auto-configuration with `base.mail.smtp.enabled=true` and no consumer `EmailSender`. Needs an SMTP server, `host`, `from`, and optional paired credentials and TLS settings under `base.mail.smtp`. | The demo includes the adapter for optional delivery. `base-mail-smtp-starter` should bundle the existing adapter and preserve the sender override. |
| `base-auth-phone` | Register `PhoneIdentityRepository` with `base.auth.phone.enabled=true` (V2, V7). Register `PhoneOtpService` and `PhoneAuthService` with `base.auth.phone.otp.enabled=true` (also V8) and supply `base.auth.phone.otp.hmac-key`. Uses the app's PostgreSQL datasource and JDBC transactions. | The demo's HTTP layer also requires `base.auth.phone.web.enabled=true` and uses rate limits and a supplied SMS sender for delivery. `base-auth-phone-starter` should expose phone identity and OTP services. Delivery adapters should remain optional. |
| `base-sms` | Plain Java SMS messages and sender contract. Real delivery requires an app-supplied `SmsSender` and its provider. | The demo adapts the contract to phone challenge delivery. Keep it usable independently as a library. |
| `base-mcp-server` | Boot auto-configuration with `base.mcp.server.enabled=true` in a servlet app. Needs HTTPS issuer and resource URLs and an OAuth authorization server for signing-key discovery and token issuance. The environment post-processor sets Spring AI's stateless HTTP transport and aligns its `/mcp` route with a dedicated security chain. | The demo contributes sample MCP capabilities behind `demo.mcp.examples.enabled` and a protected fallback for other routes. `base-mcp-server-starter` should expose MCP deliberately and keep sample capabilities application-owned. |

The demo also owns guest sessions and drafts (`base.auth.guest.enabled`, `base.auth.guest.drafts.enabled`, and V9), scheduled credential cleanup (`base.auth.cleanup.enabled`), and the settings example (V1). These have no standalone implementation JAR today.

## Wiring risks for the starter work

- **Classpath activation.** Turning a feature flag off can still leave Boot's JPA, MVC, or security auto-configuration on the classpath through the library's dependencies. A consumer that takes a JPA-backed library needs a valid datasource or must explicitly control Boot's persistence configuration. Test absence as well as activation from an application package outside the demo tree. Review redundant starter declarations and the use of framework-level dependencies in [#158](https://github.com/ShahradBagheri/spring-boot-base/issues/158).
- **Scan scope.** `base-core` and `base-web` share the `legacy.common.exception` package, and the demo and security library share `legacy.config`. For starter registration, prefer importing known components over scanning the legacy root. Keep consumer entity and repository discovery intact when adding the optional auth packages.
- **Security chain composition.** A classpath dependency on Boot Security can change servlet behavior even before a base feature is enabled. Check the fallback chain when OAuth2, bearer routes, and MCP each install a scoped chain. Test consumer overrides by behavior and check that WebSocket handshake and STOMP destination authorization remain application choices.
- **Schema ownership.** The reference SQL lives exclusively under [the demo migration directory](../demo-app/src/main/resources/db/migration/). Flyway runs the files it finds regardless of feature flags. Consumers select and version the required scripts in their own history as described in the [auth adoption guide](AUTH_MODULE_ADOPTION.md). Keep migrations, drivers, and sample profiles out of default starter activation.
- **Publication.** Stage the shared build parent alongside the BOM and library JARs so Maven can resolve the child POMs outside the source tree. CI checks staging with a fresh consumer cache. The generator and executable demo stay outside the library distribution.

The [Maven distribution decision](MAVEN_DISTRIBUTION.md) comes before the public BOM and POM work in [#157](https://github.com/ShahradBagheri/spring-boot-base/issues/157) and [#158](https://github.com/ShahradBagheri/spring-boot-base/issues/158).
