# BaseEntity contract

This is the design record for [issue #8](https://github.com/ShahradBagheri/spring-boot-base/issues/8), part of the [BaseEntity foundation epic](https://github.com/ShahradBagheri/spring-boot-base/issues/1). It reviews the existing `BaseEntity` and fixes what that class owns before the JPA code moves into `base-data-jpa` ([issue #90](https://github.com/ShahradBagheri/spring-boot-base/issues/90)). The class stays in its current package until then.

The source of truth for behavior is `src/main/java/com/notshahrad/spring_boot_base/common/entity/BaseEntity.java` together with `BaseEntityTest`. This document explains the decisions those two files encode.

## Responsibilities

| Concern | Owner | Notes |
| --- | --- | --- |
| Surrogate identifier | `BaseEntity` | One `UUID` per entity, generated by Hibernate at persist time. |
| Creation and modification timestamps | `BaseEntity` fields, populated by Spring Data JPA | `createdAt` is write-once; `updatedAt` is refreshed on every update. |
| Auditing actors | `BaseEntity` fields, value supplied by the application | The consuming application decides who the current actor is. |
| Optimistic locking | `BaseEntity` | `version` is managed by Hibernate and never set by application code. |
| Soft-deletion state and transitions | `BaseEntity` | Flag plus deletion metadata, with `softDelete` and `restore`. |
| Filtering of soft-deleted rows | Not owned — [#11](https://github.com/ShahradBagheri/spring-boot-base/issues/11) | Deferred; see decision D5. |
| Equality and hash code | Not owned — [#10](https://github.com/ShahradBagheri/spring-boot-base/issues/10) | Object identity for now; see decision D6. |
| Table names, DDL, migrations | Consuming application | Flyway migrations belong to the application ([#19](https://github.com/ShahradBagheri/spring-boot-base/issues/19)–[#21](https://github.com/ShahradBagheri/spring-boot-base/issues/21)). |
| Business timestamps, ownership, lifecycle rules | Consuming entity | `BaseEntity` only models persistence bookkeeping. |

`BaseEntity` is a `@MappedSuperclass`, not an entity. It contributes its columns and its auditing listener to every concrete subclass and must never be queried or persisted on its own.

## Decisions

### D1 — Identifier: `UUID` generated with `GenerationType.UUID`

The identifier is a `UUID` produced by Hibernate, not by a database sequence or an identity column. Hibernate generates the value in memory during `persist`, so `getId()` is populated before a flush and without a database round trip. `getId()` returns `null` only for an instance that has not been persisted yet.

Consequences:

- The application must not assign identifiers, and migrations must not add a default generator for the column.
- `equals` and `hashCode` are still unsafe by default because the identifier is absent before `persist`. Decision D6 defers that work to [#10](https://github.com/ShahradBagheri/spring-boot-base/issues/10), which must treat two transient instances as distinct.
- The column is a native `uuid` type in PostgreSQL and in the H2 test database; mapping verification belongs to [#9](https://github.com/ShahradBagheri/spring-boot-base/issues/9).

### D2 — Timestamps are `Instant`

`createdAt` and `updatedAt` are `Instant`, which is an unambiguous UTC point in time and avoids the zone and offset problems of `LocalDateTime` and `Date`. `createdAt` is declared `updatable = false`, so it is written once; `updatedAt` is rewritten by `@LastModifiedDate` on every update, including an update caused only by `softDelete` or `restore`.

Both columns are `nullable = false`, and the auditing listener assigns them while a managed instance is being persisted or updated, before the flush reaches the database. A persisted entity therefore has non-null timestamps as soon as `persist` returns. An instance that is only constructed, or mutated while detached, keeps `null` timestamps until it is persisted or merged.

A one-off probe against the H2 test database confirmed this: `persist` populated the identifier, `createdAt`, `updatedAt`, `version = 0`, and the audited actors `system` before any flush, and flushing changed none of those values.

The annotations have no effect unless the consuming application enables auditing, which is [#12](https://github.com/ShahradBagheri/spring-boot-base/issues/12)'s responsibility. This project enables it in `JpaConfig` through `@EnableJpaAuditing`.

### D3 — Auditing actors are nullable, length 100

`createdBy` and `updatedBy` describe the actor of a write. They stay nullable because not every write has an identified principal, for example a migration, a scheduled job, or an anonymous request.

The current application returns the constant `system` for every entity through a fixed `AuditorAware` bean. That is a temporary stand-in, owned by the security phase ([#25](https://github.com/ShahradBagheri/spring-boot-base/issues/25)–[#28](https://github.com/ShahradBagheri/spring-boot-base/issues/28)); the replacement supplies the authenticated principal, and `BaseEntity` must not learn about security to do it.

### D4 — Optimistic locking through `version`

`version` is a non-null `Long` managed by Hibernate through `@Version`. It starts at `0` on insert and increments on every update, which lets a stale write fail instead of silently overwriting newer data. Application code never reads or writes it except through the accessor, and a subclass must not redeclare it.

### D5 — Soft deletion is part of `BaseEntity`

**Decision: included, and specified here rather than deferred.** The state and the transitions live in `BaseEntity`; querying of deleted rows does not, and is deferred to [#11](https://github.com/ShahradBagheri/spring-boot-base/issues/11).

Inclusion is the cheaper and more honest option at this point: the state already exists, is exercised by tests, and the surviving alternative — removing it and reintroducing it after [#90](https://github.com/ShahradBagheri/spring-boot-base/issues/90) moves the class — would churn the contract that [#10](https://github.com/ShahradBagheri/spring-boot-base/issues/10) and [#11](https://github.com/ShahradBagheri/spring-boot-base/issues/11) build on. It is also consistent with the class already imposing audit columns and a version on every entity; this is a bookkeeping base class, not a minimal one.

The cost is accepted and explicit: every subclass gets the three deletion columns whether or not it uses them. An entity that must not be soft-deletable can still ignore the operations, and if a real need for a leaner base appears, a second mapped superclass without deletion state can be added later without changing this contract.

State transitions:

| Call | State before | Effect |
| --- | --- | --- |
| `softDelete(actor)` | active | `deleted = true`, `deletedAt = now`, `deletedBy = actor` (stored verbatim, not trimmed). |
| `softDelete(actor)` | deleted | Validates `actor`, then returns without changing anything. The first deletion's timestamp and actor are preserved. |
| `restore()` | deleted | `deleted = false`, `deletedAt = null`, `deletedBy = null`. |
| `restore()` | active | No-op. |

Invariants:

- `deleted` is the single source of truth, and `deleted` is `false` exactly when `deletedAt` and `deletedBy` are `null`.
- The actor is validated on every `softDelete` call, including a call on an already deleted entity: `null` raises `NullPointerException`, blank raises `IllegalArgumentException`, and more than 100 characters raises `IllegalArgumentException` so the limit fails at the call site instead of at flush. Validation never depends on prior state.
- Deletion timestamps never move backwards. Deleting, restoring, and deleting again records a new timestamp and the new actor.
- `restore` discards deletion history; there is no `restoredAt` and no audit trail of deletions. An application that needs that history must model it in its own entity.

Explicitly out of scope for `BaseEntity`, and assigned to [#11](https://github.com/ShahradBagheri/spring-boot-base/issues/11):

- Filtering deleted rows out of queries, through Hibernate restrictions or repository support.
- Replacing a physical delete with a soft delete, and cascading deletion to associations.
- Authorization rules for who may delete or restore.

**Until [#11](https://github.com/ShahradBagheri/spring-boot-base/issues/11) is implemented, `softDelete` records intent only: deleted rows remain visible to every query.** Treating a soft-deleted row as gone currently requires explicit filtering in the repository that reads it.

### D6 — Equality is deferred

`BaseEntity` does not override `equals` or `hashCode`, so entities use object identity. That is safe for persistent instances and for collections, and it avoids the failure mode where two distinct transient entities compare equal because both identifiers are `null`. [#10](https://github.com/ShahradBagheri/spring-boot-base/issues/10) owns the final strategy, must keep hash-based collections stable across `persist`, and must account for Hibernate proxies.

### D7 — No JPA lifecycle callbacks in `BaseEntity`

The class declares no `@PrePersist`, `@PostPersist`, `@PreUpdate`, `@PostUpdate`, `@PreRemove`, or `@PostLoad` methods, and none should be added speculatively. Timestamp and actor population is delegated entirely to the `AuditingEntityListener` registered once on the class, which every subclass inherits.

A future callback here needs a documented contract, a test, and a reason that auditing cannot cover it. Subclasses may register their own listeners through their own `@EntityListeners` without replacing this one.

### D8 — Accessors come from Lombok, wired explicitly

The review found that the class-level Lombok `@Getter` generated no accessors at all: the build runs on Java 25, where annotation processing is no longer implicit, and the compiler plugin had no annotation-processor configuration. `BaseEntity` compiled to a class with no identifier, timestamp, version, or deletion accessors, and `BaseEntityTest` did not compile.

Accessors stay generated by Lombok. The `maven-compiler-plugin` now declares `annotationProcessorPaths` with `${lombok.version}` and enables processing, so every build gets the same result. Do not remove that configuration: without it the build still succeeds, the source compiles unchanged, and the generated methods silently disappear.

Verify the outcome with `javap -classpath target\classes com.notshahrad.spring_boot_base.common.entity.BaseEntity`, which must list every getter.

## Rules for consuming entities

- Extend `BaseEntity`; never redeclare `id`, the audit columns, `version`, or the deletion columns.
- Keep a no-argument constructor reachable from the subclass so Hibernate can instantiate it.
- Do not mutate `id`, the audit columns, `version`, or the deletion state directly; use `softDelete` and `restore`.
- Enable JPA auditing in the application, otherwise the timestamps and actors stay `null`.
- Create the inherited columns in the application migration. A PostgreSQL table for a `BaseEntity` subclass needs:

| Column | Type | Constraints |
| --- | --- | --- |
| `id` | `uuid` | primary key |
| `created_at` | `timestamptz` | not null |
| `created_by` | `varchar(100)` | null |
| `updated_at` | `timestamptz` | not null |
| `updated_by` | `varchar(100)` | null |
| `version` | `bigint` | not null |
| `deleted` | `boolean` | not null, default `false` |
| `deleted_at` | `timestamptz` | null |
| `deleted_by` | `varchar(100)` | null |
